1 What is a Graph

⏱ 4 min ▼

A graph is just a set of things and the connections between them. The "things" are called nodes (also called vertices), and the connections are called edges. That is the entire idea. Everything else is detail.

Real world analogy: cities and roads

Picture a map. Each city is a node. Each road connecting two cities is an edge. If you can drive from Boston to New York, there is an edge between the Boston node and the New York node. A graph is nothing more than a formal way of writing down "what is connected to what."

Directed vs Undirected

  • Undirected graph — edges go both ways, like a two-way street. If A connects to B, then B connects to A. Friendship on Facebook is undirected: if you are my friend, I am your friend.
  • Directed graph — edges have a direction, like a one-way street. A → B does not mean B → A. "Following" on Twitter/X is directed: I can follow you without you following me.

Weighted vs Unweighted

  • Unweighted — an edge either exists or it doesn't. We only care about connection. "Is there a road?" Yes or no.
  • Weighted — each edge carries a number (a weight): distance, cost, time. "The road from Boston to NYC is 215 miles." Weights matter for shortest-path problems like Dijkstra, but for plain BFS/DFS we usually ignore them.
Mental model: Node = a dot. Edge = a line between two dots. Direction = does the line have an arrowhead? Weight = is there a number written on the line?

2 How to Represent a Graph in Code

⏱ 6 min ▼

A drawing of dots and lines is nice for humans, but code needs a data structure. There are two standard ways to store a graph: an adjacency list and an adjacency matrix.

Adjacency Matrix

Imagine an N×N grid where matrix[i][j] = 1 means "there is an edge from i to j," and 0 means "no edge." For 5 nodes that is a 5×5 grid of 0s and 1s.

  • Pro: checking "is there an edge between i and j?" is instant — O(1).
  • Con: it always uses O(N²) space, even if the graph has very few edges. A social network with a million users would need a million-by-million grid. That is a trillion cells. Impossible.

Adjacency List

For each node, store a list of its direct neighbors. Node 1's list is [0, 2, 3] because 1 connects to 0, 2, and 3. You only store edges that actually exist.

  • Pro: space is O(N + E) where E is the number of edges. Real-world graphs are usually sparse (few edges relative to possible edges), so this is far smaller.
  • Pro: iterating over a node's neighbors is natural and fast — exactly what BFS and DFS need.
Interview rule of thumb: Use the adjacency list unless the problem specifically demands O(1) edge lookups or the graph is tiny and dense. 95% of interview graph problems use adjacency lists. It maps perfectly onto how BFS/DFS "visit each neighbor."

Building an adjacency list from an edge list

You are usually handed edges as a list of pairs, like [[0,1],[0,4],[1,2],[1,3],[2,3],[3,4]]. Here is how to turn that into an adjacency list (undirected):

from collections import defaultdict

def build_graph(n, edges):
    # n = number of nodes, edges = list of [u, v] pairs
    adj = defaultdict(list)      # empty list for every new key
    for u, v in edges:      # unpack each edge into its two endpoints
        adj[u].append(v)         # u can reach v
        adj[v].append(u)         # v can reach u  (undirected = both ways)
    return adj

Line by line

  • from collections import defaultdict — a defaultdict(list) automatically creates an empty list the first time you touch a new key, so you never write "if the key doesn't exist, create it."
  • adj = defaultdict(list) — our graph. Keys are nodes, values are lists of neighbors.
  • for u, v in edges: — walk through every edge. Python unpacks the pair [u, v] directly into two variables.
  • adj[u].append(v) — record that u has a neighbor v.
  • adj[v].append(u) — because this graph is undirected, the edge works both ways, so we also record that v has neighbor u. If the graph were directed, you would delete this line — you'd only record u → v.
  • return adj — hand back the finished adjacency list.

Build time: O(E)Space: O(N + E)

3 The Visited Set

⏱ 4 min ▼

This is the single most important habit in graph traversal. Whenever you traverse a graph, you keep a visited set — a record of every node you have already been to.

Why? Because graphs have cycles.

In our example, 1 → 2 → 3 → 1 forms a loop. If you follow edges blindly, you'd go 1 → 2 → 3 → 1 → 2 → 3 → 1 … forever. The program never ends. It either hangs or crashes with a stack overflow.

Without a visited set: you revisit nodes, walk in circles, and loop infinitely. Trees don't have this problem (no cycles), which is why tree traversals often skip it — but general graphs almost always need it.

What "visited" actually does

Before you process a node, you ask: "have I seen this one already?" If yes, skip it. If no, mark it seen and continue. This guarantees each node is processed exactly once, which also gives graph traversal its clean O(N + E) running time.

visited = set()            # nodes we've already handled

def visit(node):
    if node in visited:    # seen before? -> stop, don't loop
        return
    visited.add(node)      # mark it NOW, before exploring neighbors
    for nei in adj[node]:   # look at each neighbor
        visit(nei)             # and recurse into the unseen ones

Line by line

  • visited = set() — a set gives O(1) membership checks (in), which is exactly what we need to keep traversal fast.
  • if node in visited: return — the guard. If we've already been here, bail out immediately. This one line is what prevents the infinite loop.
  • visited.add(node) — mark the node as seen before touching its neighbors. Marking early is critical: if you wait, two paths could enter the same node before either marks it.
  • for nei in adj[node]: — iterate this node's neighbors from the adjacency list.
  • visit(nei) — recurse. The guard at the top of each call safely ignores anything already visited.
Habit to burn in: the moment you write graph-traversal code, write the visited set in the same breath. Mark on entry, check before entering.

4 DFS — Depth First Search

⏱ 9 min ▼

Depth First Search means: pick a path and follow it as deep as you can before turning back.

Analogy: exploring a maze

You're in a maze. Your strategy: always take the first door you see, keep going until you hit a dead end, then backtrack to the last spot with an unexplored door and try that one. You go deep first, exhausting one branch completely before considering the next. That is DFS.

The call stack — what recursion really does

When a function calls itself, the computer pauses the current call, remembers exactly where it was (this saved state is a stack frame), and pushes it onto the call stack. When the inner call finishes, the top frame is popped and the paused call resumes. DFS is this stack behavior: going deeper = pushing frames; hitting a dead end and backtracking = popping frames. Recursion gives you a stack for free.

Recursive DFS

def dfs(node, adj, visited):
    if node in visited:      # already explored -> stop
        return
    visited.add(node)        # mark on entry
    print(node)              # "process" the node (here: just show it)
    for nei in adj[node]:     # for each neighbor...
        dfs(nei, adj, visited)  # ...dive deep into it first
  • if node in visited: return — the guard from Section 3. No infinite loops.
  • visited.add(node) — mark before we explore, so neighbors that point back at us are ignored.
  • print(node) — stand-in for "do the work." In real problems this is where you count, collect, or compute.
  • for nei in adj[node]: — loop over neighbors.
  • dfs(nei, ...) — the recursive dive. We fully explore nei and everything reachable from it before moving to the next neighbor. That "finish one branch completely first" is the depth-first behavior.

Iterative DFS (explicit stack)

Recursion hides a stack. Here we make it visible with our own stack list. Same order of ideas, no recursion depth limit to worry about.

def dfs_iter(start, adj):
    visited = set()
    stack = [start]              # the frontier, LIFO
    while stack:                 # while there's somewhere left to go
        node = stack.pop()       # take the MOST RECENT node (LIFO -> deep)
        if node in visited:
            continue            # skip if already done
        visited.add(node)
        print(node)              # process it
        for nei in adj[node]:     # push neighbors to revisit later
            if nei not in visited:
                stack.append(nei)
Why a stack gives the same behavior as recursion: stack.pop() always removes the most recently added item — that's LIFO (Last In, First Out). The neighbor you just pushed is the next one you explore, so you keep plunging deeper down one branch before backing up. That is exactly what the call stack does automatically during recursion.

When to use DFS vs BFS

  • Use DFS when you need to explore full paths, detect cycles, do topological sort, flood-fill a region (like counting islands), or when the solution is likely "deep." It's also the simplest to write recursively.
  • Use BFS when you need the shortest path in an unweighted graph or want to explore level by level (see next section).

Time: O(V + E)Space: O(V) — every vertex and edge is touched once; the stack/recursion can hold up to V nodes.

5 BFS — Breadth First Search

⏱ 8 min ▼

Breadth First Search explores the graph level by level: first all nodes 1 step away, then all nodes 2 steps away, and so on.

Analogy: ripples in water

Drop a stone in a pond. The ripple spreads outward in a perfect ring, one distance at a time. BFS is that ripple: it finishes everything at distance 1 before touching anything at distance 2. Because it expands in rings of equal distance, the first time BFS reaches a node, it has found the shortest path to it (in an unweighted graph).

Why a queue and not a stack?

To process nodes in the order you discovered them, you need FIFO — First In, First Out. A queue is FIFO: the first node added is the first removed, like a line at a coffee shop. That preserves the level-by-level ring order.

Contrast with DFS: DFS uses a stack (LIFO) — newest first — so it plunges deep. BFS uses a queue (FIFO) — oldest first — so it spreads wide. The only structural difference between iterative BFS and DFS is stack vs queue. Same code shape, opposite data structure.

BFS code

from collections import deque

def bfs(start, adj):
    visited = {start}            # mark start immediately
    queue = deque([start])       # FIFO frontier
    while queue:                 # until nothing left to explore
        node = queue.popleft()   # take the OLDEST node (FIFO)
        print(node)              # process it
        for nei in adj[node]:     # check each neighbor
            if nei not in visited:
                visited.add(nei) # mark WHEN enqueued, not when popped
                queue.append(nei)# add to the back of the line
  • from collections import deque — a deque gives O(1) removal from the front. A plain list's pop(0) is O(N), so always use deque for BFS.
  • visited = {start} — mark the start immediately so it never gets re-added.
  • queue = deque([start]) — our frontier, seeded with the start node.
  • while queue: — keep going while there are discovered-but-unprocessed nodes.
  • node = queue.popleft() — remove from the front. This FIFO order is what makes it breadth-first.
  • for nei in adj[node]: — look at every neighbor.
  • if nei not in visited: — only handle new nodes.
  • visited.add(nei) — mark when you enqueue, not when you dequeue. If you wait until popping, the same node could be added to the queue several times before it's ever processed — a classic bug.
  • queue.append(nei) — push to the back of the line so it's handled after everything currently ahead of it.

When to use BFS vs DFS

  • BFS wins for shortest path in unweighted graphs — the ripple reaches nearest nodes first, so the first arrival is the shortest.
  • BFS wins for "level" or "minimum steps" problems (word ladder, rotting oranges, minimum moves).
  • DFS wins for path existence, cycle detection, connected components / flood fill, topological sort, and anything where recursion is cleaner.

Time: O(V + E)Space: O(V) — same asymptotics as DFS; the queue can hold up to V nodes.

6 LC 200 — Number of Islands

⏱ 8 min ▼

The problem in plain English

You're given a 2D grid of '1's (land) and '0's (water). An island is a group of '1's connected horizontally or vertically (not diagonally). Count how many separate islands there are.

Intuition — the NeetCode way

Here's the key reframe: the grid is a graph in disguise. Every land cell is a node. Two land cells are connected (share an edge) if they're directly up/down/left/right of each other. An island is just a connected component — a clump of nodes all reachable from each other.

So the question "how many islands?" becomes "how many connected components of land are there?" To count components, we do this: scan the grid; every time we hit a land cell we haven't seen, that's a brand-new island — so add 1, then DFS to flood the entire island and mark all its cells visited so we never count it again.

Why DFS makes sense: starting from one land cell, DFS naturally spreads to every connected land cell (up/down/left/right, recursively), covering the whole island in one call. What the visited set represents: "this land has already been counted as part of some island." Here we can save memory by sinking visited land — overwriting '1' with '0' — instead of a separate set.

Full solution

class Solution:
    def numIslands(self, grid):
        if not grid:
            return 0
        rows, cols = len(grid), len(grid[0])
        count = 0

        def dfs(r, c):
            # out of bounds, or water -> stop
            if r < 0 or r >= rows or c < 0 or c >= cols or grid[r][c] == '0':
                return
            grid[r][c] = '0'          # "sink" this land = mark visited
            dfs(r + 1, c)              # down
            dfs(r - 1, c)              # up
            dfs(r, c + 1)              # right
            dfs(r, c - 1)              # left

        for r in range(rows):
            for c in range(cols):
                if grid[r][c] == '1':   # found new, unvisited land
                    count += 1          # it's a fresh island
                    dfs(r, c)             # flood the whole island
        return count

Every line, tied back to the intuition

  • if not grid: return 0 — empty grid, no islands. Guard against edge cases.
  • rows, cols = len(grid), len(grid[0]) — grid dimensions, used for bounds checks.
  • count = 0 — our island counter (= number of connected components).
  • def dfs(r, c): — floods one island starting from cell (r, c). This is the "spread to all connected land" step.
  • if r < 0 or ... or grid[r][c] == '0': return — the base case. Stop if we walk off the grid or hit water. Water isn't part of the island; edges of the grid bound it.
  • grid[r][c] = '0' — this is the visited mark. By sinking the land to water, we guarantee we never revisit or recount this cell. It's the memory-saving alternative to a visited set.
  • dfs(r+1,c) … dfs(r,c-1) — recurse into all four orthogonal neighbors. This is how one call spreads across the entire connected island.
  • for r in range(rows): for c in range(cols): — scan every cell.
  • if grid[r][c] == '1': — a land cell that's still '1' hasn't been flooded yet, so it belongs to an island we haven't counted.
  • count += 1 — new connected component found → increment. This line runs once per island, because the dfs right after it sinks the rest of that island.
  • dfs(r, c) — flood-fill so the entire island turns to water and won't be counted again.
  • return count — total number of islands.

Complexity

Time: O(rows × cols) Every cell is visited a constant number of times — once by the outer scan, and at most once by a DFS that sinks it.

Space: O(rows × cols) Worst case the recursion stack goes as deep as the number of cells — imagine a grid that's entirely land; DFS could stack every cell before returning.

7 LC 133 — Clone Graph

⏱ 8 min ▼

The problem

You're given a reference to one node of a connected undirected graph. Return a deep copy of the whole graph — a completely independent set of new nodes with the same structure and connections.

What "cloning" really means

You can't just return the node you were given, and you can't reuse its neighbors. A deep copy means brand-new node objects that mirror the originals. If the original has node A connected to B, your clone must have a new A' connected to a new B' — and critically, if two original nodes both point to the same neighbor, both clones must point to the same single cloned neighbor, not two separate copies.

Intuition

Use DFS to walk the graph. The problem: graphs have cycles, so as we clone we'll keep bumping into nodes we've already cloned. We need to remember them. So we keep a hashmap that maps each original node → its clone.

The rule: when we arrive at a node, if it's already in the map, return the existing clone (don't clone it again — that both prevents infinite loops and keeps shared neighbors shared). If it's new, create its clone, record it in the map, then recursively clone all its neighbors and attach them.

The hashmap plays two roles at once: it's our "visited set" (stops cycles) and our lookup table (old node → new node), so every reference points to the correct single copy.

Full solution

# Definition for a Node.
class Node:
    def __init__(self, val=0, neighbors=None):
        self.val = val
        self.neighbors = neighbors if neighbors else []

class Solution:
    def cloneGraph(self, node):
        if not node:
            return None
        old_to_new = {}              # original node -> its clone

        def dfs(cur):
            if cur in old_to_new:      # already cloned? return the clone
                return old_to_new[cur]
            copy = Node(cur.val)      # make the new node
            old_to_new[cur] = copy   # record BEFORE recursing (breaks cycles)
            for nei in cur.neighbors:  # clone each neighbor...
                copy.neighbors.append(dfs(nei))  # ...and wire it up
            return copy

        return dfs(node)

Every line, tied back to the intuition

  • if not node: return None — empty graph edge case.
  • old_to_new = {} — the hashmap that is both visited-tracker and old→new lookup.
  • def dfs(cur): — returns the clone of cur, creating it if needed.
  • if cur in old_to_new: return old_to_new[cur] — the crucial line. If we've seen this original before, hand back the clone we already made. This stops infinite recursion on cycles and ensures shared neighbors map to one shared clone.
  • copy = Node(cur.val) — create the new node with the same value (but empty neighbors for now).
  • old_to_new[cur] = copy — record the mapping BEFORE recursing. If we recursed first, a cycle back to cur would try to clone it again → infinite loop. Registering early means the guard above catches the loop.
  • for nei in cur.neighbors: — go through the original's connections.
  • copy.neighbors.append(dfs(nei)) — clone each neighbor (or fetch its existing clone) and attach it to our copy. This rebuilds the exact same structure with new objects.
  • return copy — hand back this node's finished clone.
  • return dfs(node) — kick it off from the given node; get back the clone of the whole graph.

Complexity

Time: O(V + E) We create each node once and walk each edge once while wiring up neighbors.

Space: O(V) The hashmap holds one entry per node, plus recursion depth up to V.

8 Templates to Know Cold

These three are the backbone of nearly every graph problem. Learn them until you can type them without thinking.

1 · DFS recursive

def dfs(node, adj, visited):
    if node in visited:        # guard: don't revisit
        return
    visited.add(node)          # mark on entry
    # --- do work with node here ---
    for nei in adj[node]:       # explore each neighbor
        dfs(nei, adj, visited)    # dive deep first

2 · DFS iterative (explicit stack)

def dfs_iter(start, adj):

    while stack:
        node = stack.pop()       # newest first -> depth
        if node in visited:
            continue
        visited.add(node)
        # --- do work with node here ---
        for nei in adj[node]:
            if nei not in visited:
                stack.append(nei)

3 · BFS (queue)

from collections import deque

def bfs(start, adj):
    visited = {start}            # mark start right away
    queue = deque([start])       # FIFO frontier
    while queue:
        node = queue.popleft()   # oldest first -> breadth
        # --- do work with node here ---

                visited.add(nei)     # mark when ENQUEUED

★ Summary — Key Things to Remember

⏱ 2 min ▼
Graph = nodes + edges

Directed (one-way) vs undirected (two-way). Weighted vs unweighted. That's the whole vocabulary.

Use adjacency lists

O(N+E) space, natural neighbor iteration. Matrices only for dense/tiny graphs.

Always keep visited

Mark on entry, check before entering. Without it, cycles loop forever.

DFS = stack = deep

LIFO. Recursion is a stack for free. Great for components, paths, cycles, flood fill.

BFS = queue = wide

FIFO. First arrival = shortest path in unweighted graphs. Mark visited on enqueue.

Both are O(V + E)

Each node and edge touched once. Space O(V) for the frontier/stack.

Islands = components

Grid is a graph. Scan; each new land cell +1 island, then DFS to sink it.

Clone = DFS + hashmap

old→new map is both visited-set and lookup. Record clone before recursing.

✎ Self Test — Check Your Understanding

⏱ 6 min ▼

These test whether you understand, not whether you memorized. Think through each before revealing.

Q1. You run BFS and DFS on the same connected graph from the same start node. Will they always visit the same set of nodes? Will they visit them in the same order? ▶

Same set, different order. Both eventually reach every node reachable from the start, so the visited sets are identical. But BFS expands level by level (queue/FIFO) while DFS plunges deep (stack/LIFO), so the order differs. If a problem only asks "which nodes are reachable," either works; if it asks "shortest number of steps," you need BFS.

Q2. In BFS, why do we mark a node visited when we add it to the queue rather than when we remove it? ▶

Because a node can be a neighbor of several nodes already in the queue. If you only mark on removal, the same node gets enqueued multiple times before it's ever processed — wasting work and potentially breaking shortest-path guarantees. Marking on enqueue ensures each node enters the queue exactly once.

Q3. In the Number of Islands solution, why does count += 1 run exactly once per island even though an island can have hundreds of land cells? ▶

Because the moment we find a new land cell and increment, we immediately call dfs, which sinks (marks visited) every cell of that island to '0'. By the time the outer scan reaches those other cells, they're already water, so the if grid[r][c] == '1' check fails and we don't increment again. One increment per connected component.

Q4. In Clone Graph, what specifically breaks if you move old_to_new[cur] = copy to after the neighbor loop instead of before it? ▶

You get infinite recursion on any cycle. Suppose A and B are neighbors of each other. Cloning A recurses into B, which recurses back into A. If A wasn't registered in the map yet, the guard if cur in old_to_new misses, so A gets cloned again → into B again → forever. Registering the clone before recursing lets the guard catch the cycle.

Q5. Someone hands you a graph with 1,000,000 nodes but only about 2,000,000 edges (very sparse). Which representation do you choose and roughly how much memory does the other one waste? ▶

Adjacency list, easily. It uses O(N + E) ≈ 3 million entries. An adjacency matrix uses O(N²) = 1,000,000² = one trillion cells — completely infeasible. The matrix only pays off when the graph is dense (E close to N²) or you need constant-time "is there an edge between i and j?" lookups.

Q6. You need the minimum number of moves to solve a puzzle where each state connects to a few next states, all moves cost 1. DFS or BFS, and why? ▶

BFS. All edges cost the same (1 move), so this is a shortest-path-in-an-unweighted-graph problem. BFS explores states in increasing order of distance, so the first time it reaches the goal state it has used the fewest moves. DFS might find the goal via a long, winding path first and give a wrong (non-minimal) answer.
