1 Directed Graphs & DAGs

⏱ 5 min▼

A directed graph is a graph where edges have a direction — an arrow. Edge A → B means "you can go from A to B," but not necessarily from B to A. Think one-way streets.

What is a cycle?

A cycle is a path that leads back to where it started by following the arrows: A → B → C → A. You can go around forever. Cycles are the enemy of ordering, because if A must come before B, B before C, and C before A, then… there's no valid starting point. It's a contradiction.

What is a DAG?

A DAG is a Directed Acyclic Graph — a directed graph with no cycles. Because nothing loops back on itself, you can always find a consistent order to process the nodes. This is exactly why DAGs matter for topological sort: topological sort only exists on a DAG.

Analogy: university course prerequisites

"Calculus I" must come before "Calculus II," which comes before "Calculus III." Draw an arrow from each course to the course it unlocks. In a sane curriculum there are no cycles — you'd never have a rule that says "you need C to take A, and A to take C." That prerequisite graph is a DAG, and a topological sort of it is simply a valid order to take all the classes.

Calc II
Calc III
Physics

Arrows point from prerequisite → course it unlocks. No cycles = it's a DAG.

Remember: Cycle in a directed graph = no valid ordering exists. DAG = ordering always exists. Half of these problems reduce to "is this graph a DAG?"

2 Topological Sort

⏱ 12 min▼

A topological sort is a linear ordering of a directed graph's nodes such that for every edge A → B, A comes before B in the ordering. It's "an order that respects all the dependencies."

Analogy: getting dressed

You must put on socks before shoes, and underwear before pants. You physically cannot put shoes on before socks. There are many valid orders (socks → underwear → pants → shirt → shoes is fine; so is underwear → socks → shirt → pants → shoes), but all of them keep socks before shoes. A topological sort produces one such valid order.

Only works on a DAG. If there's a cycle — say A depends on B and B depends on A — there is no valid order, and a correct topological-sort algorithm will detect that and report failure (it produces fewer nodes than exist).

Kahn's Algorithm (BFS-based)

The core idea is in-degree: a node's in-degree is the number of arrows pointing into it — i.e., how many prerequisites it still has. The algorithm:

  1. Compute every node's in-degree.
  2. Start with all nodes whose in-degree is 0 (no prerequisites) — put them in a queue.
  3. Pop a node, add it to the result order. For each of its neighbors, decrement their in-degree by 1 (we just "finished" one of their prerequisites).
  4. If a neighbor's in-degree hits 0, all its prerequisites are done — add it to the queue.
  5. Repeat until the queue is empty. If the result contains every node, success. If not, there was a cycle.

Kahn's algorithm code

from collections import deque, defaultdict

def topo_kahn(n, edges):
    adj = defaultdict(list)
    indeg = [0] * n              # in-degree of every node
    for u, v in edges:            # edge u -> v
        adj[u].append(v)             # u unlocks v
        indeg[v] += 1              # v gains one prerequisite

    queue = deque([i for i in range(n) if indeg[i] == 0])  # start nodes
    order = []
    while queue:
        node = queue.popleft()       # a node with no remaining prereqs
        order.append(node)           # commit it to the order
        for nei in adj[node]:         # for everything it unlocks...
            indeg[nei] -= 1         # ...one prereq done
            if indeg[nei] == 0:      # all prereqs done?
                queue.append(nei)    # it's now ready

    return order if len(order) == n else []  # [] means cycle
  • indeg = [0]*n — one counter per node; how many arrows point in.
  • adj[u].append(v) and indeg[v] += 1 — for edge u → v, record the neighbor and bump v's in-degree.
  • queue = deque([... if indeg[i]==0]) — seed the queue with every node that has no prerequisites. These are our valid starting points.
  • node = queue.popleft() — take a node with zero remaining prerequisites; it's safe to place next.
  • order.append(node) — commit it to the output order.
  • indeg[nei] -= 1 — we just finished node, which was a prerequisite for nei, so lower its count.
  • if indeg[nei] == 0: queue.append(nei) — if that was its last prerequisite, it's now ready to be placed.
  • return order if len(order)==n else [] — the cycle check. If a cycle exists, those nodes never reach in-degree 0, never enter the queue, and are missing from order. A short list = cycle = no valid ordering.

Time: O(V + E)Space: O(V + E)

DFS-based topological sort (post-order)

The other approach uses DFS. The key insight: a node should appear in the ordering only after everything it depends on is placed — so we add a node to our result after we've fully explored all of its outgoing edges (its "descendants"). That's post-order. Because we build the list bottom-up, we reverse it at the end.

Why add AFTER visiting all neighbors? If node A → B, we must finish B (and everything B leads to) first. By appending A only after the recursion into B returns, B lands in the list before A. Then reversing makes A come before B — exactly the dependency order we want. 
def topo_dfs(n, edges):
    adj = defaultdict(list)
    for u, v in edges:
        adj[u].append(v)

    visited = [0] * n     # 0=unseen, 1=in progress, 2=done
    order = []
    has_cycle = [False]

    def dfs(node):
        if visited[node] == 1:      # hit a node on the current path -> cycle
            has_cycle[0] = True
            return
        if visited[node] == 2:      # already finished -> skip
            return
        visited[node] = 1          # mark IN PROGRESS
        for nei in adj[node]:
            dfs(nei)               # finish all descendants first
        visited[node] = 2          # mark DONE
        order.append(node)          # POST-ORDER: add after neighbors

    for i in range(n):
        if visited[i] == 0:
            dfs(i)
    if has_cycle[0]:
        return []
    return order[::-1]         # reverse post-order = topo order
  • visited uses three states: 0 unseen, 1 in-progress, 2 done. The "in-progress" state is how DFS detects cycles.
  • if visited[node]==1: has_cycle=True — if we reach a node that's still on our current recursion path, we've looped back → cycle → no valid order.
  • if visited[node]==2: return — fully processed already; nothing to do.
  • visited[node]=1 — mark that this node is on the active path.
  • for nei in adj[node]: dfs(nei) — recurse into all descendants first.
  • visited[node]=2 then order.append(node) — post-order append. The node is recorded only after all its dependents are done, so it sits before them once reversed.
  • return order[::-1] — reverse to turn "deepest-first" into "dependency-first."

Time: O(V + E)Space: O(V + E)

3 LC 207 — Course Schedule

⏱ 7 min▼

The problem

There are numCourses courses labeled 0 to numCourses-1. You're given prerequisites where [a, b] means "to take course a, you must first take course b." Return True if you can finish all courses, else False.

The reframe

Each course is a node; each prerequisite [a, b] is a directed edge b → a ("b unlocks a"). "Can I finish all courses?" is exactly "Is this graph a DAG (no cycle)?" If there's a cycle — course X needs Y, Y needs X — you can never start, so return False. No cycle → return True.

Intuition — Kahn's algorithm

Run Kahn's topological sort and just count how many courses we manage to finish (pop from the queue). If a cycle exists, the nodes in that cycle never hit in-degree 0, so we finish fewer than numCourses. If we finish all of them, there was no cycle.

Full solution

from collections import deque, defaultdict

class Solution:
    def canFinish(self, numCourses, prerequisites):
        adj = defaultdict(list)
        indeg = [0] * numCourses
        for a, b in prerequisites:   # must take b before a
            adj[b].append(a)             # edge b -> a
            indeg[a] += 1              # a has one more prereq

        queue = deque([c for c in range(numCourses) if indeg[c] == 0])
        finished = 0                   # how many courses we completed

        while queue:
            course = queue.popleft()     # no remaining prereqs
            finished += 1            # take it
            for nxt in adj[course]:      # courses it unlocks
                indeg[nxt] -= 1
                if indeg[nxt] == 0:
                    queue.append(nxt)

        return finished == numCourses    # all done -> no cycle

Every line, tied to the intuition

  • adj[b].append(a) / indeg[a] += 1 — build the graph: b unlocks a, and a gains a prerequisite. In-degree = "prereqs left to satisfy."
  • queue = deque([... indeg[c]==0]) — courses with no prerequisites; you can take these right away.
  • finished = 0 — our counter, standing in for the cycle test.
  • course = queue.popleft() — a course whose prerequisites are all met.
  • finished += 1 — mark it complete.
  • indeg[nxt] -= 1 — completing course removes a prerequisite from everything it unlocks.
  • if indeg[nxt]==0: queue.append(nxt) — a course whose last prerequisite just cleared becomes takeable.
  • return finished == numCourses — the answer. If a cycle existed, its courses never reached in-degree 0, so finished falls short → False. Finishing all means the graph is a DAG → True.

Complexity

Time: O(V + E) V = numCourses, E = number of prerequisites. Each node enqueued once, each edge relaxed once.

Space: O(V + E) Adjacency list plus in-degree array and queue.

4 LC 210 — Course Schedule II

⏱ 6 min▼

How it differs from 207

Problem 207 asked a yes/no question: can you finish? Problem 210 asks for the actual order — return any valid ordering of courses to take, or an empty array [] if it's impossible (a cycle exists).

Intuition

It's the same Kahn's algorithm — but instead of only counting finished courses, we record each course in an order list as we pop it. The order in which nodes leave the queue is a valid topological order. At the end, if the order contains every course, return it; otherwise a cycle blocked us, so return [].

Full solution

from collections import deque, defaultdict

class Solution:
    def findOrder(self, numCourses, prerequisites):
        adj = defaultdict(list)
        indeg = [0] * numCourses
        for a, b in prerequisites:   # take b before a
            adj[b].append(a)             # edge b -> a
            indeg[a] += 1

        queue = deque([c for c in range(numCourses) if indeg[c] == 0])
        order = []                       # the actual sequence

        while queue:
            course = queue.popleft()
            order.append(course)         # record it in the order
            for nxt in adj[course]:
                indeg[nxt] -= 1
                if indeg[nxt] == 0:
                    queue.append(nxt)

        return order if len(order) == numCourses else []

Every line, tied to the intuition

  • Graph building and the queue seed are identical to 207 — same DAG, same in-degree bookkeeping.
  • order = [] — instead of an integer counter, we keep the actual list of courses.
  • order.append(course) — the one meaningful change. Each time a course becomes takeable (all prereqs cleared) and we pop it, we append it. The pop-order respects every prerequisite, so it's a valid topological sort.
  • indeg[nxt] -= 1 / if indeg[nxt]==0: queue.append(nxt) — same dependency-clearing logic as before.
  • return order if len(order)==numCourses else [] — if we placed every course, the order is complete and valid; a shortfall means a cycle, so return [] per the problem spec.
Takeaway: 207 and 210 are the same algorithm. 207 returns count == n; 210 returns the list itself. Learn one, you've learned both.

Complexity

Time: O(V + E)Space: O(V + E) Same as 207 — the output list doesn't change the asymptotics.

5 What is Union Find

⏱ 9 min▼

Union Find (also called Disjoint Set Union, or DSU) is a data structure for tracking which group each element belongs to, when groups can merge over time.

Analogy: friend groups

If A and B are friends, they're in one group. If B and C are friends, then C joins that group too — now A, B, and C are all one group, even though A and C never met directly. Union Find answers "are these two people in the same group?" and lets you "merge two groups" efficiently.

Two operations

  • Find(x) — return a representative ("leader"/"root") of x's group. Two elements are in the same group iff they have the same root.
  • Union(x, y) — merge the groups containing x and y into one.

Naive approach

Keep a parent array where each element points to a parent. Follow parents upward until you reach a node that points to itself — that's the root. To union, make one root the parent of the other. Simple, but if you're careless the tree can become a long chain (A→B→C→D→…), so find degrades to O(N). Two optimizations fix this.

Optimization 1: Path compression

When you call find(x) and walk up to the root, you already know the root — so re-point every node along the way directly to the root. The tree gets flatter each time. Next time those nodes are looked up, they're one hop from the root.

BEFORE find(4) — a tall chain

3

4
AFTER find(4) — flattened

Path compression: after finding 4's root (1), nodes 2, 3, and 4 all point straight at 1. Future lookups are O(1)-ish.

Optimization 2: Union by rank

Rank is roughly the height of a tree. When merging two trees, always attach the shorter tree under the taller one's root. This keeps the combined tree as shallow as possible. If you did the opposite — hang the tall tree under the short one — you'd make it taller and slower.

Together these are magic: path compression + union by rank make find and union run in almost O(1) — technically O(α(N)), where α is the inverse Ackermann function, which is ≤ 4 for any input you'll ever see. Practically constant.

6 Union Find Code Template

⏱ 7 min▼

This is the class to memorize. It has both optimizations built in.

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))   # each node is its own parent (root)
        self.rank = [1] * n            # tree height/size estimate

    def find(self, x):
        if self.parent[x] != x:        # not a root yet
            self.parent[x] = self.find(self.parent[x])  # path compression
        return self.parent[x]          # return the root

    def union(self, x, y):
        rx, ry = self.find(x), self.find(y)  # roots of each group
        if rx == ry:                   # already same group
            return False              # nothing merged
        if self.rank[rx] < self.rank[ry]:   # make rx the taller root
            rx, ry = ry, rx
        self.parent[ry] = rx           # attach shorter under taller
        if self.rank[rx] == self.rank[ry]:  # tie -> taller by one
            self.rank[rx] += 1
        return True                   # a real merge happened

Every line

  • self.parent = list(range(n)) — start with N separate groups; every node is its own root (parent[i] == i).
  • self.rank = [1]*n — each single-node tree has rank 1. Rank guides union-by-rank.
  • def find(self, x): — return x's root, compressing the path on the way.
  • if self.parent[x] != x: — if x isn't already a root, keep climbing.
  • self.parent[x] = self.find(self.parent[x]) — path compression. Recursively find the root, then point x directly at it. This flattens the tree so future finds are fast.
  • return self.parent[x] — hand back the root.
  • rx, ry = self.find(x), self.find(y) — find both roots. Same root ⇒ already connected.
  • if rx == ry: return False — they're already in one group; report "no merge." (Handy for cycle detection and counting.)
  • if self.rank[rx] < self.rank[ry]: rx, ry = ry, rx — ensure rx is the taller (higher-rank) root so we attach correctly.
  • self.parent[ry] = rx — union by rank: hang the shorter tree under the taller root, keeping height minimal.
  • if self.rank[rx] == self.rank[ry]: self.rank[rx] += 1 — only when both had equal rank does the merged tree get one level taller.
  • return True — a genuine merge occurred (two groups became one).

How to use it

uf = UnionFind(5)          # nodes 0..4, all separate
uf.union(0, 1)             # group {0,1}
uf.union(1, 2)             # group {0,1,2}
uf.union(3, 4)             # group {3,4}

print(uf.find(0) == uf.find(2))  # True  (same group)
print(uf.find(0) == uf.find(4))  # False (different groups)

# number of distinct groups:
groups = len({uf.find(i) for i in range(5)})  # 2

find / union: O(α(N)) ≈ O(1)Space: O(N)

7 LC 721 — Accounts Merge

⏱ 11 min▼

The problem in plain English

Each account is [name, email1, email2, ...]. Two accounts belong to the same person if they share at least one email. Merge all accounts of the same person: output the name followed by all their emails, sorted, deduplicated. Different people can share the same name, so the name is not an identifier — shared emails are.

The reframe

Think of every email as a node. Within one account, all its emails are connected (they clearly belong together). If two accounts share an email, that shared email links their whole email-sets. So the task becomes: find connected components of emails, then group each component under its owner's name. "Connected components" screams Union Find.

Intuition using Union Find

Union all emails within each account together (e.g., union the first email with every other email in that account). Shared emails automatically stitch accounts into one component, because that email has one root no matter which account touched it. Then, for each email, look up its root and bucket emails by root. Each bucket = one person's full email set.

Concrete walk-through

Accounts:

  • A: John, j1@x, j2@x
  • B: John, j3@x, j1@x
  • C: Mary, m1@x
1
Account A: union j1@x with j2@x. Component: {j1, j2}.
2
Account B: union j3@x with j1@x. Since j1@x is already with j2, now {j1, j2, j3} — accounts A and B merged through the shared email j1.
3
Account C: union m1@x with itself. Component: {m1}.
4
Group by root: {j1, j2, j3} → John; {m1} → Mary. Sort emails inside each group.
✓
Output: ["John","j1@x","j2@x","j3@x"] and ["Mary","m1@x"].

Full solution

from collections import defaultdict

class Solution:
    def accountsMerge(self, accounts):
        parent = {}
        def find(x):
            parent.setdefault(x, x)      # first time seeing x -> its own root
            if parent[x] != x:
                parent[x] = find(parent[x])  # path compression
            return parent[x]
        def union(x, y):
            parent[find(x)] = find(y)  # merge the two roots

        email_to_name = {}
        for acc in accounts:
            name = acc[0]
            first = acc[1]
            for email in acc[1:]:      # every email in this account
                email_to_name[email] = name   # remember its owner's name
                union(first, email)   # tie all emails of this account together

        groups = defaultdict(list)
        for email in email_to_name:  # bucket emails by their root
            groups[find(email)].append(email)

        result = []
        for root, emails in groups.items():
            name = email_to_name[root]
            result.append([name] + sorted(emails))  # name + sorted emails
        return result

Every line, tied to the intuition

  • parent = {} — a dict-based Union Find (emails are strings, so a dict beats an array).
  • parent.setdefault(x, x) — lazily register an email as its own root the first time we see it.
  • find with parent[x] = find(parent[x]) — the root lookup with path compression, so components collapse flat.
  • union(x, y): parent[find(x)] = find(y) — connect two emails by pointing one root at the other. This is what makes emails in the same account (and across accounts sharing an email) one component.
  • email_to_name[email] = name — record who owns each email, so after grouping we can label each bucket. (Safe because same-component emails share the same person.)
  • union(first, email) — the core linking step. Union the account's first email with each of its other emails, so the whole account is one component. When another account reuses one of these emails, its union pulls both accounts into a single component through that shared email.
  • groups[find(email)].append(email) — bucket every email under its component's root. Each bucket is one person's complete email set.
  • result.append([name] + sorted(emails)) — build the output line: the owner's name, then all emails sorted as required.

Complexity

Let N = total number of emails across all accounts.

Time: O(N · α(N) + N log N) Unions/finds are near-constant; the sorted(emails) per group sums to O(N log N), which dominates.

Space: O(N) Parent map, name map, and the groups all scale with the number of emails.

8 LC 1258 — Synonymous Sentences

⏱ 11 min▼

The problem

You're given a list of synonyms pairs like ["happy","joy"] and a sentence text. Any word can be replaced by any of its synonyms — and synonyms are transitive (if happy≈joy and joy≈cheerful, then happy≈cheerful). Return all possible sentences you can form, sorted lexicographically.

The reframe

Each word is a node; each synonym pair is an edge. Transitive synonyms = connected components. So group words into synonym-sets with Union Find. Then, for each word in the sentence that belongs to a synonym group, its replacement choices are all words in that group. Generate every combination across the sentence's positions.

Intuition

  1. Union every synonym pair, forming groups of interchangeable words.
  2. For each group root, gather the sorted list of words in that group.
  3. Walk the sentence. For a word with synonyms, its options are its whole group (sorted); otherwise the only option is the word itself.
  4. Backtrack to build every combination, then sort the results.

Full solution

from collections import defaultdict

class Solution:
    def generateSentences(self, synonyms, text):
        parent = {}
        def find(x):
            parent.setdefault(x, x)
            if parent[x] != x:
                parent[x] = find(parent[x])   # path compression
            return parent[x]
        def union(x, y):
            parent[find(x)] = find(y)     # merge two synonym groups

        for a, b in synonyms:           # build synonym components
            union(a, b)

        # group every known word by its root
        groups = defaultdict(list)
        for word in parent:
            groups[find(word)].append(word)
        for root in groups:
            groups[root].sort()          # lexicographic within a group

        words = text.split()
        options = []                     # choices for each position
        for w in words:
            if w in parent:            # word has synonyms
                options.append(groups[find(w)])
            else:
                options.append([w])      # no synonyms -> itself only

        result = []
        def backtrack(i, path):
            if i == len(options):
                result.append(" ".join(path))
                return
            for choice in options[i]:   # try each synonym at position i
                backtrack(i + 1, path + [choice])

        backtrack(0, [])
        return result                   # already sorted (groups sorted)

Every line, tied to the intuition

  • find / union — the standard dict-based Union Find. Words are the elements.
  • for a, b in synonyms: union(a, b) — step 1: connect each synonym pair. Transitivity is automatic — chaining unions merges chains of synonyms into one component.
  • groups[find(word)].append(word) — step 2: bucket words by component root. Each bucket is one synonym set.
  • groups[root].sort() — sort each group so choices come out lexicographically; this makes the final result sorted without an extra global sort of full sentences.
  • words = text.split() — break the sentence into positions.
  • if w in parent: options.append(groups[find(w)]) — step 3: if the word is part of a synonym group, its options are the entire (sorted) group.
  • else: options.append([w]) — a word with no synonyms can only be itself.
  • def backtrack(i, path): — step 4: build sentences position by position.
  • if i == len(options): result.append(" ".join(path)) — a full sentence is assembled; record it.
  • for choice in options[i]: backtrack(i+1, path+[choice]) — try every synonym at this position and recurse. This enumerates the full cartesian product of choices.
  • return result — because each position's options are pre-sorted and we iterate them in order, the sentences come out lexicographically sorted.

Complexity

Let S = number of synonym pairs, L = words in the sentence, and K = the largest number of choices per position.

Time: O(S·α + total output size) Building groups is near-linear; generating sentences is inherently O(number of results × sentence length) because there can be up to KL sentences and you must emit all of them.

Space: O(number of words + output) Union Find and group buckets are linear; the result list holds every generated sentence.

1 · Topological Sort — Kahn's (BFS)

from collections import deque, defaultdict

def topo_kahn(n, edges):
    adj = defaultdict(list)
    indeg = [0] * n
    for u, v in edges:        # edge u -> v
        adj[u].append(v)
        indeg[v] += 1          # v gains a prerequisite
    q = deque([i for i in range(n) if indeg[i] == 0])
    order = []
    while q:
        node = q.popleft()       # no prereqs left
        order.append(node)
        for nei in adj[node]:
            indeg[nei] -= 1
            if indeg[nei] == 0:
                q.append(nei)
    return order if len(order) == n else []  # [] = cycle

2 · Topological Sort — DFS (post-order)

def topo_dfs(n, edges):
    adj = defaultdict(list)
    for u, v in edges:
        adj[u].append(v)
    state = [0] * n            # 0=unseen 1=on-path 2=done
    order, cycle = [], [False]

    def dfs(node):
        if state[node] == 1:      # back-edge -> cycle
            cycle[0] = True; return
        if state[node] == 2:
            return
        state[node] = 1
        for nei in adj[node]:
            dfs(nei)
        state[node] = 2
        order.append(node)          # POST-ORDER append

    for i in range(n):
        if state[i] == 0:
            dfs(i)
    return [] if cycle[0] else order[::-1]  # reverse!

3 · Union Find class

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))   # self-rooted
        self.rank = [1] * n

    def find(self, x):
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])  # compress
        return self.parent[x]

    def union(self, x, y):
        rx, ry = self.find(x), self.find(y)
        if rx == ry:
            return False              # already connected
        if self.rank[rx] < self.rank[ry]:
            rx, ry = ry, rx
        self.parent[ry] = rx           # small under big
        if self.rank[rx] == self.rank[ry]:
            self.rank[rx] += 1
        return True

★ Summary — Key Things to Remember

⏱ 2 min▼
DAG = no cycles

Topological sort exists only on a DAG. A cycle means no valid order.

Kahn's = in-degree + queue

Start at in-degree 0, decrement neighbors, enqueue when they hit 0. Fewer than n processed = cycle.

DFS topo = post-order + reverse

Append after visiting neighbors, then reverse. Three-color states catch cycles.

207 vs 210

Same algorithm. 207 returns count==n; 210 returns the order list itself.

Union Find = groups

find = which group (root); union = merge. Same root ⇒ same component.

Two optimizations

Path compression flattens on find; union by rank attaches small under big. Together ≈ O(1).

Connected components → Union Find

Accounts Merge & Synonyms both reduce to "group connected things," the DSU signature.

Cycle detection two ways

Kahn: leftover nodes. DFS: revisiting an on-path (state 1) node.

✎ Self Test — Check Your Understanding

⏱ 7 min▼

Understanding checks, not recall. Reason it out before revealing.

Q1. In Kahn's algorithm, you finish and find len(order) == 4 but the graph has 6 nodes. What does that tell you, and where did the other 2 nodes go? ▶

There's a cycle involving those 2 nodes. They (and any node whose only path in runs through the cycle) never reached in-degree 0, so they were never enqueued or placed in order. A cycle means no valid topological ordering exists — which for Course Schedule means "you can't finish all courses."

Q2. In DFS-based topo sort, why must we reverse the list at the end? What would happen if we returned it as-is? ▶

We append each node in post-order — after its descendants are done — so dependencies land in the list before the nodes that depend on them. That's the reverse of what we want. If we returned it un-reversed, edge A → B would show B before A, violating the ordering. Reversing puts every prerequisite ahead of what it unlocks.

Q3. Someone removes union-by-rank from the Union Find class but keeps path compression. Is it still correct? Is it still fast? ▶

Still correct — grouping logic is unchanged; find still returns the right root. Still fast in practice — path compression alone gives O(log N) amortized, and combined-with-nothing is close enough for interviews. But you lose the near-O(1) guarantee that both optimizations together provide. Best answer: keep both; each protects against a different worst case (tall chains).

Q4. In Accounts Merge, why can't we just group accounts by name? Give a case where that fails. ▶

Because different people can share a name. Two accounts both named "John" with no shared emails are different people and must stay separate. Conversely, one person might appear under accounts that share an email. Identity is defined by shared emails (connected components), not the name — which is exactly why we union on emails and only use the name as a label at the end.

Q5. Both this file's grouping problems (Accounts Merge, Synonymous Sentences) could technically be solved with DFS/BFS connected components instead of Union Find. Why is Union Find often the cleaner choice here? ▶

Because the connections arrive as incremental pairwise merges (this email links to that one; this word is a synonym of that one). Union Find is built exactly for "keep merging pairs and ask what's connected," with near-constant operations and no need to build an explicit adjacency list first. DFS/BFS also work, but you'd construct the graph, then traverse it — more setup for the same result. When the problem is phrased as "merge these pairs into groups," reach for Union Find.

Q6. Why does sorting each synonym group in LC 1258 make the final list of sentences come out lexicographically sorted, without sorting the sentences themselves? ▶

Backtracking generates sentences by iterating each position's options in order. If every position's option list is sorted, the leftmost position varies slowest and its smallest choice is emitted first, then the next position, and so on — exactly how lexicographic order is defined across the sentence. The cartesian product enumerated in sorted-per-position order is the globally sorted order, so no final sort of full strings is needed.
